# 发布 Open Browser Use v1.0.0

## 目标

从已合并并通过 CI 的 `main` 发布首个稳定正式版本 `v1.0.0`，确保所有版本源、
GitHub Release 制品、npm/PyPI 包、Homebrew formula 和 Chrome Web Store 提交流程
保持一致并有可核验结果。

## 范围

- 包含：统一版本号、发布记录、完整 CI、tag、GitHub Release、npm、PyPI、
  Homebrew 和 Chrome Web Store 发布状态跟进。
- 不包含：新增产品功能、改变既有协议或取消 Chrome Web Store 中的已有审核任务。

## 背景

- 相关文档：`docs/CICD.md`、`docs/CHROME_WEB_STORE_RELEASE.md`、
  `docs/releases/README.md`。
- 相关代码路径：`apps/chrome-extension/manifest.json`、
  `cmd/open-browser-use/main.go`、`packages/*`、`.github/workflows/`。
- 已知约束：tag 推送不可原地修改；Chrome Web Store 若存在 active submission，
  自动流程会记录 `ACTIVE_SUBMISSION` 并跳过，不影响其他发布目标。

## 风险

- 风险：跨包版本遗漏导致制品或 registry 版本不一致。
- 缓解方式：对全部已知版本源做精确搜索，并在发布前运行完整 CI 和本地打包。
- 风险：不可逆 tag 或 registry 发布在验证前发生。
- 缓解方式：先确认 `v1.0.0` 未被占用，完成本地验证和 commit 审计后再推 tag。
- 风险：各发布 workflow 独立运行，局部失败可能被忽略。
- 缓解方式：逐个跟进 release、npm、PyPI、Homebrew workflow，并核对真实 registry
  与 GitHub Release 资产；单独记录 Chrome Web Store 的提交或跳过原因。

## 里程碑

1. 盘点未发布变化、版本源和发布自动化。
2. 完成 `1.0.0` 版本同步、文档与发布记录。
3. 完成本地 CI、打包和版本一致性验证。
4. 提交、推送 `main` 和 `v1.0.0` tag。
5. 跟进并核验所有发布目标，归档本计划。

## 验证方式

- 命令：`make ci`、`OPEN_BROWSER_USE_VERSION=1.0.0 ./scripts/release-package.sh`。
- 手工检查：版本源只出现 `1.0.0`，commit 不含禁止 trailer，tag 指向预期 commit。
- 观测检查：GitHub Actions 全部完成；GitHub Release 资产齐全；npm/PyPI/Homebrew
  可查询到 `1.0.0`；Chrome Web Store 结果有明确状态。
